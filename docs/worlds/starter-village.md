# 雾溪村：框架验收世界设计

## 定位

雾溪村是沙盘框架的第一个可运行世界，用来验证配置创世、单实例 SQLite、Agent 知识边界、感知、探索、沟通、长时 Action、行为树、非线性需求、Intent 校验、BT 演化和 God Agent 干预。它不承载一条固定主线；世界状态、Agent 目标和玩家选择共同生成故事。

首版使用 9 个 Agent 和 1 个玩家槽位。9 个 Agent 足以覆盖治理、安全、粮食、医疗、制造、探索、信息、贸易和世界真相九个领域，同时形成可观察的社会网络。玩家以外来者身份进入，身份、目标和能力在进入时创建。

## 世界前提

雾溪村位于灰林边缘，村中心的旧井下方存在一座古老的“根门”。根门维持村庄与灰林之间的边界，创村者曾与森林记忆订立契约。当前契约正在减弱，雾气、灰热病和失踪事件逐步增加。村民知道的只是局部事实：村长知道旧契约的片段，守卫知道北门出现异常，草药师知道病源与水有关，学者知道根门的位置，其他人通过探索、沟通和公开记录逐步形成自己的知识。

世界真相由 Platform 持有。Agent 初始只获得配置中的 `knowledge_seed`，玩家只知道入村路线、广场、旅店和公开村规。秘密地点、未公开事件和其他 Agent 的私有知识不会进入普通观察结果。

游戏时间直接使用分钟。Platform 可以一次推进 1 分钟或一段连续分钟，但 LLM 只看到 `world_minute`、日期和时刻，不看到内部执行步编号。1 天为 1,440 分钟，1 周为 10,080 分钟，1 月为 43,200 分钟。长时采集、巡逻、研究、锻造和战斗行为使用 `duration.minutes`；每日反思、每周个体创新、每周局部世界创新和每月结构创新由分钟日历触发。

### Agent 状态

Agent 的持久状态和运行状态都进入 SQLite。持久状态包括身份、属性、能力、需求、库存、关系、知识、记忆、信念和目标；运行状态包括当前地点、`status`、活动 BT、活动 Action、进度、剩余分钟、伤势、疾病和状态效果。

首版状态枚举为：`idle`、`executing`、`paused`、`injured`、`unconscious`、`fleeing`、`dead`。攻击、事故、疾病和环境事件由 Platform 产生伤势事件；伤势记录部位、严重程度、疼痛、出血、恢复时间和影响能力。伤势会改变 `eligible_bt_catalog`，例如昏迷 Agent 不能移动、攻击或沟通，受伤守卫可以报警但不能执行高强度巡逻。治疗、休息和恢复 Action 只能通过 Platform 更新伤势。

LLM 看到的状态是精简摘要，例如“何砚，北门，受伤 20%，可执行：报警、撤离、低强度防御；当前 Action：调查痕迹，剩余 34 分钟”，而不是整张数据库记录。

### Agent 初始关系

- 林泊信任何砚，依赖梁禾，警惕费兰，压制苏巫。
- 何砚尊重陆行舟的能力，但反对其独自深入灰林。
- 乔宁和苏巫共享部分秘密，乔宁不接受苏巫的高风险实验。
- 田岩依赖梁禾的粮食供应，费兰试图购买他的星铁碎片。
- 余歌是信息交换中心，与所有 Agent 保持中等信任，秘密偏向玩家获得完整事实。

关系强度、信任、恐惧、债务和敌意写入配置初值，后续只由 Platform 事件更新。关系边携带证据事件，Agent 的主观关系记忆与世界真实关系分开保存。

## 玩家入口

玩家不是预先写死的 Agent。`player_template.yaml` 定义玩家进入时可选择的出身、初始目标、能力标签和公开知识。玩家在河桥触发 `player.entered`，获得广场、旅店、村规和当前公开时间的知识，未加入势力，声誉为 0。

玩家使用和 Agent 相同的 Platform Intent 接口。玩家可以选择可执行 BT、发起对话、接受委托、探索区域或提交计划；Platform 对玩家和 Agent 使用相同的资源、可见性、Action 和事件规则。

## 框架验收场景

| 场景 | 触发 | 观察结果 |
|---|---|---|
| 配置创世 | 创建新的雾溪村实例 | 9 个 Agent、17 个通用元动作、19 棵基础 BT、地点、规则和开局事件进入独立 SQLite |
| 玩家进入 | 在河桥创建玩家 | 玩家只获得公开知识，不获得根门和 Agent 私有记忆 |
| 长时行动 | 陆行舟执行灰林测绘或田岩锻造 | 数百至上千分钟只推进 Action，完成时产生结果事件 |
| 战斗与中断 | 北门威胁触发攻击、防御、撤离和报警 | Platform 结算伤害、体力、威胁、关系和紧急中断 |
| 探索发现 | 玩家或猎人探索灰林边缘 | 产生 `exploration.completed`，执行者获得带证据和置信度的知识 |
| 沟通传播 | 玩家从余歌处询问北门异常，再向何砚求证 | 形成两条带来源的 testimony，Agent 置信度可以不同 |
| 需求冲突 | 粮食减少且灰热病扩散 | 粮仓、守卫、草药师和村长的非线性驱动进入不同临界区 |
| BT 演化 | 乔宁提交“采药并隔离病源”的新 BT | 非法节点被 Platform 拒绝，错误回传给 Agent，修正后注册新版本 |
| 世界演化 | 周/月结算触发 God Agent | 只提交经校验的实体、事件或规则变化，结果写入 SQLite |

## 配置入口

完整的属性、元动作和基础 BT 清单见 [starter-village-catalog.md](starter-village-catalog.md)；给 LLM 的简明英文目录见 [starter-village-agent-catalog.md](starter-village-agent-catalog.md)。配置文件是 Platform 的规范输入；LLM 读取的是 Platform 根据当前状态过滤后的精简目录，不直接读取原始 YAML。AgentView 是运行时生成的临时投影，不作为世界事实文件保存。

雾溪村中的 BT 用来组合通用能力：例如 `craft_meal` BT 调用 `craft_recipe` Action 读取 `cooked_meal` Recipe；`defend_village` BT 先报警，再选择防御或撤离；`explore_greywood` BT 组合移动和探索，完成后由独立互动会话传播信息。取粮分为 `get_food`（先移动到粮仓）和 `get_food_here`（已在粮仓），避免隔空改变库存。Recipe 只描述材料和产物，Action 负责按分钟执行，BT 负责控制流，Platform 负责状态变化。

配置包位于 `worlds/starter_village/`：

- `manifest.yaml`：配置版本、随机种子和文件清单。
- `setting.yaml`：世界前提、时间尺度和隐性真相索引。
- `world_state.yaml`：初始世界属性、初始事实和 Agent 出生位置。
- `locations.yaml`：地点、可见性、路线和资源节点。
- `objects.yaml`：物品、材料、工具、文书和可发现对象。
- `factions.yaml`：势力、规范、权限和关系初值。
- `agents.yaml`：Agent 身份、终极目标、信念、需求、知识种子、关系和初始 BT。
- `actions.yaml`：元动作契约、目标、条件、成本、持续时间、效果和 Platform effect pipeline。
- `capabilities.yaml`：采集、农作、烹饪、锻造、战斗、探索、沟通和研究能力定义。
- `recipes.yaml`：熟食、口粮和药剂等输入、输出、工作站和能力要求。
- `behavior_trees.yaml`：BT 定义、条件、节点和结果契约。
- `rules.yaml`：分钟效果、需求曲线、社会规则和世界约束。
- `evolution.yaml`：反思、创新、危机触发器和 God Agent 周期限制。
- `opening_events.yaml`：玩家入口、开局异常和首日事件。
- `player_template.yaml`：玩家创建时可选的出身和能力。
